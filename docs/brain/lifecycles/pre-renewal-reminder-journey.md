# Pre-renewal reminder → next-order journey (end-to-end)

The Retention flow that, a few days before each renewal, reaches a subscriber with a reminder, drops them into a mini-site **next-order journey** that is the portal's full subscription editor (swap, quantity, add, remove, skip, date, frequency, and an in-journey cancel with the same save offers), and measures the whole thing as a **self-running, person-level 50/50 test** — treatment vs a true holdout — surfaced live on an owner-only retention dashboard. The CEO is notified only on a guardrail trip or the verdict.

This lifecycle is the permanent home of the completed goal **"Pre-renewal reminders + next-order journey, proven by a self-running 50/50 test"** ([[../functions/retention]] · proposed by [[../functions/ceo]]). It traces the four milestones that landed, each already documented in depth on its own page; this page is the spine that joins them.

## The chain

**1 — Daily eligibility scan (M2).** The [[../inngest/pre-renewal-reminders]] `pre-renewal-reminder-cron` runs `0 13 * * *`, deliberately **after** the morning charge crons ([[../inngest/internal-subscription-renewals]] / [[../inngest/shopify-subscription-renewals]], `0 10 * * *`) so a sub charged today isn't also reminded. Per workspace, [[../libraries/pre-renewal-reminders]] `scanEligibleReminders` selects `active` subs on both live engines (`billing_source` `shopcx`+`internal`) renewing in a ±1-day band around 5 days out (`PRE_RENEWAL_WINDOW_DAYS`), **excludes** subs in an active [[../tables/dunning]] cycle and subs edited in the last `PRE_RENEWAL_RECENT_EDIT_DAYS` (3), and **collapses to one reminder per person** via the [[../tables/customer_links]] `group_id` (earliest in-window `next_billing_date` → stable `renewal_window_key`).

**2 — Arm assignment + ledger (M3 harness).** Each person-group asks the [[../libraries/subscriber-experiments]] harness `assignArm(ws, 'pre-renewal-reminder', customerId)` for its sticky arm — assigned once at first eligibility on the identity GROUP, never re-bucketed, honouring the harness kill switch. A [[../tables/pre_renewal_reminders]] ledger row is written **before any send** (unique on `(workspace_id, group_id, renewal_window_key)` — a `23505` cleanly means "already reminded"). Holdout groups stop here (`status='holdout'`, nothing new). This is the clean counterfactual the verdict rests on.

**3 — The sends (M2).** Treatment mints a `next-order` [[../tables/journey_sessions]] row (earliest sub pre-selected, `ticket_id` null — proactive) and sends the transactional email CTA via [[../libraries/email]] `sendJourneyCTA` ([[../integrations/resend]]) to every treatment customer. For SMS-marketing-consented customers only, `maybeSendConsentedSms` also texts the same CTA at the recipient's local 11:00 ([[../libraries/marketing-text-timezone]] — quiet hours never breached), honouring STOP/unsubscribe ([[../integrations/twilio]]); every intended + suppressed send is stamped on the ledger with the arm so the opt-out/complaint guardrails can read it.

**4 — The journey (M1).** The CTA opens the [[../journeys/next-order]] mini-site — the portal's subscription editor delivered inside the journey. Every edit POSTs to `src/app/api/journey/[token]/edit/route.ts` and dispatches through the **same shared executors the portal uses** ([[../libraries/remedy-actions]] `executeLineItemAction` → [[../libraries/subscription-items]], plus `src/lib/commerce/subscription.ts` for skip/date, [[../libraries/subscription-frequency]] `changeSubscriptionFrequency` for frequency) — no forked edit path, three-engine routing. The catalog + consumable/in-stock rule are the Portal's via [[../libraries/portal__editable-catalog]] (`loadEditableCatalog` / `isSwappableConsumable`), and the Portal-parity mutation guards (first-delivery lock, failed-payment block, selectability + consumable) are applied **in the edit route before dispatch** (`runPortalParityGuards`) — the earlier "portal mutation guards intact [via the executors]" claim was wrong; the guards live in the Portal handlers, not the executors (fixed 2026-11-22). A failed edit from a ticketless reminder session opens a follow-up ticket (`ensureJourneyFollowUpTicket`) so a human always owns the promise. The in-journey "Cancel subscription" runs the real cancel sequence (reason → [[../libraries/remedy-selector]] `selectRemedies` save offers → confirm) so the journey and [[customer-portal]] / [[cancel-flow]] surfaces stay in sync. **Verify-before-report**: a failed edit never tells the customer it worked — it leaves the ticket open, raises a high-severity [[../tables/dashboard_notifications]] row, and promises a human (the 2026-11-16 save-flow bug class). Lifecycle events (`opened`/`edited`/`skipped`/`cancelled`/`saved`) land in [[../tables/journey_step_events]] keyed by session.

**5 — Measurement (M3) + dashboard (M4).** [[../libraries/subscriber-experiment-metrics]] `computeExperimentMetrics` rolls up each arm's **90-day net revenue per customer** (`Σ orders.total_cents − Σ settled order_refunds`, netting only `succeeded`+`settled`) over a per-group window anchored on `assigned_at`, plus the secondary rates (voluntary cancel, skip, swap/add-on, distinct products). The [[../libraries/reminder-results-sdk]] `getReminderTestResults` composes those metrics + the send ledger + the journey events + the harness row into one treatment-vs-holdout shape for `GET /api/workspaces/[id]/analytics/renewal-reminder` → the owner-only [[../dashboard/retention-renewal-reminder]] page (two arm cards, primary-metric strip, guardrail strip, verdict banner).

## Why a new experiment harness (not storefront-experiments)

The 50/50 test deliberately did **not** reuse [[../libraries/storefront-experiments]]: that framework is visitor/render grain with content-patch variants — the wrong grain (visitor, not person) and the wrong lever (content, not send/no-send). The subscriber harness buckets the person identity GROUP once and persists it under a UNIQUE `(experiment_id, group_id)` constraint, and pre-registers the sample size (`powerCalcRequiredN`) + stop rule at `createExperiment` time so the verdict is credible rather than decided after seeing data. Tables: [[../tables/customer_lifecycle_experiments]] + [[../tables/customer_lifecycle_experiment_assignments]].

## Supervisable autonomy (north star)

The whole flow optimizes a bounded proxy (90-day net revenue per person) while [[../functions/retention]] owns the objective. Every new node shipped with the trio: the reminder cron is a `retention`-owned `MONITORED_LOOPS` row ([[../libraries/control-tower-node-registry]]) with a [[../tables/kill_switches]] ancestry and an `emitCronHeartbeat` on every tick (incl. the no-eligible / switch-off paths); the harness is the `tool:subscriber-experiment-harness` node whose switch `assignArm` honours before minting any new assignment. A tripped guardrail means escalate (auto-pause + one deduped CEO notification), never continue. The CEO sees nothing unless a guardrail trips or the verdict lands.

- **M1 — Next-order journey** → [[../journeys/next-order]] (`next-order-journey-editor` spec). In-journey editor + cancel at portal parity through the shared executors.
- **M2 — Renewal reminder sends** → [[../inngest/pre-renewal-reminders]] + [[../libraries/pre-renewal-reminders]] + [[../tables/pre_renewal_reminders]] (`pre-renewal-reminder-sends` spec). Email + consented SMS, arm-stamped ledger.
- **M3 — Self-running 50/50 test** → [[../libraries/subscriber-experiments]] + [[../libraries/subscriber-experiment-metrics]] (`subscriber-experiment-harness` + `subscriber-experiment-guardrails-verdict` specs). Sticky person-level assignment, pre-registered N + stop rule, net-revenue measurement.
- **M4 — Results dashboard** → [[../dashboard/retention-renewal-reminder]] + [[../libraries/reminder-results-sdk]] (`renewal-reminder-results-dashboard` spec). Owner-only live view of both arms, guardrail strip, verdict banner.
